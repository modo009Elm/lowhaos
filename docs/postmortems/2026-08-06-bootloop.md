# LowhaOS — Bootloop Post-Mortem, 2026-08-06

> **Build:** `lineage-23.2-20260806-UNOFFICIAL-FP6.zip` (first OTA with the full LowhaOS stack)
> **Outcome:** flashed cleanly, bootlooped, rollback attempt failed, device recovered via recovery + reflash
> **Author:** Fable

---

## 1. What broke

`system_server` crashed at `systemReady()` and was restarted by zygote ~50 times:

```
FATAL EXCEPTION IN SYSTEM PROCESS: main
java.lang.IllegalStateException: Signature|privileged permissions not in privileged permission allowlist:
  {app.lowha.settings (/system/priv-app/LowhaSettings): android.permission.PACKAGE_USAGE_STATS}
    at AppIdPermissionPolicy.onSystemReady(AppIdPermissionPolicy.kt:1823)
    at PackageManagerService.systemReady(PackageManagerService.java:4372)
```

### Root cause — a PARTITION mismatch, not a name mismatch

| | Installed to |
|---|---|
| `LowhaSettings.apk` | `/system/priv-app/` |
| `privapp-permissions-lowha.xml` | `/system_ext/etc/permissions/` |

**Android requires the privapp allowlist to live on the same partition as the app it authorises.** An allowlist in `system_ext` does not cover an app in `/system`. PackageManager therefore saw `app.lowha.settings` requesting a `signature|privileged` permission with no allowlist entry at all, and — by design — aborted boot rather than granting it.

`LowhaCoreService` sits in the *same* directory with the *same* mismatch and never tripped it, because it declares `sharedUserId="android.uid.system"`. It runs as the system UID and gets those permissions directly, bypassing the privapp check. That asymmetry is why only Settings failed.

### Why no gate caught it

Every build gate this session was a **compile-time** check. This is a **runtime** contract enforced by PackageManager at first boot. `m LowhaSettings` was green; the APK was valid; the allowlist was valid; the *relationship between them* was wrong. Nothing in Soong validates it.

The risk was flagged in the plan ("a wrong privapp entry is a boot failure, not a build failure") and the mitigation applied was verifying **package names** with `aapt2` — which were all correct. The partition dimension was never checked.

## 2. The second mistake — the rollback made it worse

On seeing the bootloop I ran `fastboot --set-active=a` to return to the known-good 2026-07-20 build. It failed: the device reached the Fairphone splash and dropped back to fastboot. The retry counter proved it was genuinely attempting and failing (`7` after `--set-active`, `6` after one attempt) rather than being skipped.

**Cause: the FP6 uses virtual A/B.** There are not two independent copies of the OS. There is one set of partitions in `super` plus *snapshots* for the updated slot. Once the new slot boots, a **merge** writes the snapshot data permanently into `super`, **consuming the old slot's contents**. Slot `b` booted to `system_server` ~50 times — far more than enough for that merge to run. `fastboot getvar snapshot-update-status` returned `none`, consistent with a merge already completed.

By the time the rollback was attempted, slot `a`'s system/vendor/product no longer existed.

**Lesson: on a virtual A/B device, `--set-active` is not a rollback once the new slot has booted.** Treating it like classic A/B cost the fallback build. The correct assumption is that flashing an OTA which boots at all is effectively one-way.

**What actually saved the device:** `recovery` lives on its own partition outside `super` and was untouched, so `fastboot reboot recovery` worked and sideload remained available.

## 3. Fixes in the new build

### 3.1 The defect — two independent fixes

**a. Remove the permission entirely.** `LowhaSettings` never needed `PACKAGE_USAGE_STATS`. All usage data arrives over AIDL from `LowhaCoreService`, which already holds it. Least privilege; the root cause disappears.

**b. Co-locate app and allowlist.** `system_ext_specific: true` added to `LowhaSettings/Android.bp`, so it installs to `/system_ext/priv-app/` — the same partition the allowlist is copied to. Any *future* privileged permission now works instead of bricking boot.

Either fix alone is sufficient. Both are in.

### 3.2 A gate for this class of failure

`/workspace/check-privapp-partitions.sh` — audits every priv-app against the allowlist partition and fails the build before an OTA is produced. Accounts for the `sharedUserId=android.uid.system` exemption so it doesn't false-positive on `LowhaCoreService`.

```
allowlist partition: TARGET_COPY_OUT_SYSTEM_EXT
LowhaCoreService  priv=yes partition=system      sysuid=1   ← exempt, runs as system UID
LowhaSettings     priv=yes partition=system_ext  sysuid=0   ← now matches
AuroraStore       priv=yes partition=system_ext  sysuid=0   ← matches
PASS: no partition mismatches
```

### 3.3 A stale-artifact gate

The rebuild chain aborts if `out/.../system/priv-app/LowhaSettings/` still exists after the move. A leftover copy on the old partition would reproduce the identical bootloop while the source looked correct.

### 3.4 Chain aborts instead of building

`rebuild-chain.sh` runs: partition gate → build → verify new partition → verify no stale copy → **only then** `bacon`. Any failure stops before spending 45 minutes producing an unflashable OTA.

## 4. What is still NOT protected

Honest limits of the new gates:

- They catch **this** class (privapp partition). They do not catch other runtime-only contracts.
- Four runtime-only defects were found by inspection this session, none by any gate: the browser role pinned to a non-existent package, the privapp entry naming a package that never installs, `app.lowha.permission.LOWHA_CORE` referenced but never declared, and the service bind action missing from the intent-filter. All were found by reading, not building.
- **The only real test is booting the device.** Every gate is a filter to make that test cheaper, not a substitute for it.
- There is now **no fallback build on the device**. Until a known-good OTA boots, recovery + sideload is the only route back.

---

## 5. Process changes worth keeping

1. **Verify the artifact, not the build result.** A green build proves compilation. Checking `lowha_blocklist_file` in the compiled `vendor_sepolicy.cil`, and the commit strings in the shipped SetupWizard dex, proved the *code shipped*. Both caught real risk.
2. **Gate cheaply and often.** Eight `m <module>` gates at ~12 min caught eight real errors that would otherwise have surfaced 45–60 min into a full build.
3. **Assume OTAs are one-way on virtual A/B.** Do not rely on slot rollback. Keep a known-good OTA zip on the laptop — that, not the other slot, is the fallback.
4. **Read the file back after scripted edits.** One `PRODUCT_PACKAGES` edit silently no-op'd (heredoc escaping) while reporting success. Caught only by reading the file.
